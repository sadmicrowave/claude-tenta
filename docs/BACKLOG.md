## Worker choice: count the whole route-trip cost, as a tie-break below the immediate factors
`sched._rank` orders: preferred/dedicated, stale, held, fits now, most capacity free, `wait_s` (time until the worker NOTICES a job: 5 s assumed for Direct, the idle fetch interval for GitHub), load per core, name. In a fleet mixing Direct and GitHub workers, one more free capacity point beats a much faster route, and `wait_s` ignores the rest of the trip (push, result coming back by polling, a slow link) and is assumed, not measured. Change: replace `wait_s` with an estimate of the full trip (pickup + result return, from the settings and recent measured round trips); rank it above "most capacity free" only when the job fits on both, keep preferred/dedicated, freshness, held and "fits now" above it; show both estimates in the "why chosen" text. Needs its own scoped branch (it reorders real job placement).

**Addition to the worker-choice entry (pace depends on the worker's mode).** A worker checks the queue at a pace that depends on its mode: active every `fetch_s` (5 s), idle every `idle_fetch_s` (90 s), asleep every `sleep_fetch_s` (300 s); it publishes its `mode` and a single `pickup_max_s` that is the WORST of the three (`cli.py` state publish), and `sched.wait_s` uses that. So today a worker that is already awake (recent job, or just woken) is costed as if it were asleep. Change: cost the pickup from its CURRENT published mode (and how long it has been in it), and when this computer has just sent it a job (it will be active for the next jobs, `sent_pending`) use the active pace for the follow-ups; a wake that this computer triggers should switch the estimate to the active pace immediately, not after the next reading. The estimate must also be re-read when the reading is stale (the mode may have changed). Direct transports are unaffected (5 s always). Test with the same fleet shape as the real one: a GitHub worker idle against one awake, and the same two after a job was just sent.

## "Device not listed": a double-click setup tool for the target computer (per operating system)
Idea (from the user): many people cannot open PowerShell as administrator, install and configure OpenSSH or do the other setup a worker needs before it can be found and reached. In `ct-setup install` / `add-worker`, when the scan does not find the computer, add one more numbered choice, "Device not listed: download and install setup tools on the target device by hand". Then: (1) choose the target operating system from a fixed list (Windows 10/11, macOS, Linux, ...); (2) a system file-save dialog opens to choose where to save the setup tool (on a computer with no dialog available, ask for a folder instead); (3) the tool is a self-contained file the person double-clicks on the target computer: per OS (Windows: a signed or clearly named .cmd/.ps1 launcher that asks for administrator rights by itself, installs and starts the OpenSSH server, opens the firewall for it, creates the key-login access for the administrator account from a public key we embed, and prints/shows the address to give back; macOS: a .command that enables Remote Login; Linux: a shell script). Needs design: how the target's address and the key come back (a printed line to type, or a small code), the security of an embedded public key (no secret in the file), what the tool changes (shown before it does anything, one confirm), uninstall, and that it never ships anything private. Also fixes the real gap found on the Windows VM: `sshd` was not installed and admin elevation had to be done by hand.

**Addition to the setup-tool entry (the return path; from the user, then discussed).** The tool is GENERATED per run, not precompiled: `ct-setup` builds the script for the chosen operating system with this computer's LAN address, its public key and a one-time token and secret already inside (nothing private). The script sets up SSH on the target, then CHECKS IN to this computer: its address, hostname and SSH host-key fingerprint. Meanwhile `ct-setup` listens briefly (TCP, bound to the LAN address, one check-in, times out in about 15 minutes) and prints "waiting for the device to check in". The check-in must be authenticated, not just tokened, because a LAN is shared: first version = HMAC-SHA256 over the message with the per-run secret plus a timestamp and nonce (the host rejects a bad, old or replayed message; stdlib on the host; built into PowerShell, macOS and Linux `openssl dgst`), no certificate to manage. Later hardening options: encrypt the body (encrypt-then-MAC with AES-CBC; PowerShell 5.1 has no AES-GCM, the host would need `openssl`), or serve HTTPS with a pinned self-signed certificate (encryption + authentication + replay protection; harder to pin from PowerShell 5.1). Nothing secret crosses the wire in either direction (public key out, address and fingerprint back), so the real need is authenticity and integrity; confidentiality of a hostname is secondary. A person confirms what checked in (IP, hostname, fingerprint) before it is trusted; the host then pins that fingerprint so the later key-login connection is verified. If the device never checks in, fall back to typing its address.
