## Worker choice: count the whole route-trip cost, as a tie-break below the immediate factors
`sched._rank` orders: preferred/dedicated, stale, held, fits now, most capacity free, `wait_s` (time until the worker NOTICES a job: 5 s assumed for Direct, the idle fetch interval for GitHub), load per core, name. In a fleet mixing Direct and GitHub workers, one more free capacity point beats a much faster route, and `wait_s` ignores the rest of the trip (push, result coming back by polling, a slow link) and is assumed, not measured. Change: replace `wait_s` with an estimate of the full trip (pickup + result return, from the settings and recent measured round trips); rank it above "most capacity free" only when the job fits on both, keep preferred/dedicated, freshness, held and "fits now" above it; show both estimates in the "why chosen" text. Needs its own scoped branch (it reorders real job placement).

**Addition to the worker-choice entry (pace depends on the worker's mode).** A worker checks the queue at a pace that depends on its mode: active every `fetch_s` (5 s), idle every `idle_fetch_s` (90 s), asleep every `sleep_fetch_s` (300 s); it publishes its `mode` and a single `pickup_max_s` that is the WORST of the three (`cli.py` state publish), and `sched.wait_s` uses that. So today a worker that is already awake (recent job, or just woken) is costed as if it were asleep. Change: cost the pickup from its CURRENT published mode (and how long it has been in it), and when this computer has just sent it a job (it will be active for the next jobs, `sent_pending`) use the active pace for the follow-ups; a wake that this computer triggers should switch the estimate to the active pace immediately, not after the next reading. The estimate must also be re-read when the reading is stale (the mode may have changed). Direct transports are unaffected (5 s always). Test with the same fleet shape as the real one: a GitHub worker idle against one awake, and the same two after a job was just sent.

## "Device not listed": a double-click setup tool for the target computer (per operating system)
Idea (from the user): many people cannot open PowerShell as administrator, install and configure OpenSSH or do the other setup a worker needs before it can be found and reached. In `ct-setup install` / `add-worker`, when the scan does not find the computer, add one more numbered choice, "Device not listed: download and install setup tools on the target device by hand". Then: (1) choose the target operating system from a fixed list (Windows 10/11, macOS, Linux, ...); (2) a system file-save dialog opens to choose where to save the setup tool (on a computer with no dialog available, ask for a folder instead); (3) the tool is a self-contained file the person double-clicks on the target computer: per OS (Windows: a signed or clearly named .cmd/.ps1 launcher that asks for administrator rights by itself, installs and starts the OpenSSH server, opens the firewall for it, creates the key-login access for the administrator account from a public key we embed, and prints/shows the address to give back; macOS: a .command that enables Remote Login; Linux: a shell script). Needs design: how the target's address and the key come back (a printed line to type, or a small code), the security of an embedded public key (no secret in the file), what the tool changes (shown before it does anything, one confirm), uninstall, and that it never ships anything private. Also fixes the real gap found on the Windows VM: `sshd` was not installed and admin elevation had to be done by hand.

**Addition to the setup-tool entry (the return path; from the user, then discussed).** The tool is GENERATED per run, not precompiled: `ct-setup` builds the script for the chosen operating system with this computer's LAN address, its public key and a one-time token and secret already inside (nothing private). The script sets up SSH on the target, then CHECKS IN to this computer: its address, hostname and SSH host-key fingerprint. Meanwhile `ct-setup` listens briefly (TCP, bound to the LAN address, one check-in, times out in about 15 minutes) and prints "waiting for the device to check in". The check-in must be authenticated, not just tokened, because a LAN is shared: first version = HMAC-SHA256 over the message with the per-run secret plus a timestamp and nonce (the host rejects a bad, old or replayed message; stdlib on the host; built into PowerShell, macOS and Linux `openssl dgst`), no certificate to manage. Later hardening options: encrypt the body (encrypt-then-MAC with AES-CBC; PowerShell 5.1 has no AES-GCM, the host would need `openssl`), or serve HTTPS with a pinned self-signed certificate (encryption + authentication + replay protection; harder to pin from PowerShell 5.1). Nothing secret crosses the wire in either direction (public key out, address and fingerprint back), so the real need is authenticity and integrity; confidentiality of a hostname is secondary. A person confirms what checked in (IP, hostname, fingerprint) before it is trusted; the host then pins that fingerprint so the later key-login connection is verified. If the device never checks in, fall back to typing its address.

## One class, a command per operating system (and a manifest of equivalents)
Question from the user: can a job sent from a Linux/macOS computer run on a Windows worker, or must each class be written for Windows? Answer found in the code: a job names only the CLASS and its parameters; the command is the class's `run: [program, args...]` list in the WORKER's own registry (no shell), so delivery works for any worker, but the `run` list itself is OS-specific as soon as it names a program or path that does not exist on the other OS (`sh`, `grep`, `tar`, `/tmp/...`; a Windows job's PATH is only the system folders, so even `python` or `pytest` need the tools folder named). Today a Windows worker refuses `network: false` and Claude classes (registry.platform_problems) but does not check that the program exists. Idea (user): offload ONE command and let the orchestrator choose the delivery per target OS; if it cannot convert, ask the user for the Windows version. Proposed shape (decide when scoped): (1) a class may carry per-platform commands (`run` plus `run_windows`, or a `run` map keyed by platform), validated per worker platform; (2) a class whose `run` uses only programs on a short PORTABLE list (python, git, node, ...) is offered everywhere the program is installed; (3) a command-equivalents manifest (POSIX program -> Windows program and argument rules) used only to SUGGEST a Windows variant to the person, who approves it like any class change: not silent conversion at delivery time, because the registry is the review boundary and a wrong conversion runs a different program than the one approved; (4) `ct-run classes` shows "no Windows variant" for a class a Windows worker cannot run, with the prompt to provide one; (5) the worker checks the program exists on its own PATH/tool folders before accepting the class. Related: paths in params (`/tmp`, `~`) and environment differences.

## Enterprise deployment (future feature; so far everything assumes a home or small-office LAN)
Idea (from the user): make this work at enterprise level: enterprise-grade network equipment and routing, multi-subnet IP routing, corporate access-policy intake and adherence, DMZ and VPN, and others. Areas to design (none scoped):
- Reaching workers: scanning and discovery do not cross subnets, so an explicit inventory (DNS names, CIDR lists, an imported list) replaces the scan; VPN reachability, DMZ placement, bastion / jump hosts (ProxyJump) for the Direct transport.
- Transport and network policy: egress allowlists and HTTP(S) proxies for git, pip and downloads (the tools installer and the update fetch assume direct internet), TLS-inspecting proxies with a corporate CA, firewalls that allow only named ports and sources, the GitHub transport through a proxy or an enterprise GitHub host.
- Identity and access: SSH certificates signed by a CA (host and user) instead of individual authorized_keys and deploy keys; domain-joined Windows computers (domain or group-managed service accounts instead of a local `ctworker`); SSO and role-based access for who may send which class to which fleet.
- Policy and audit: change-approval workflows and corporate policy intake (a policy file that limits classes, networks and tool folders fleet-wide), central log shipping to a SIEM, who sent what and when.
- Software supply chain: internal package and git mirrors, an offline or air-gapped release path, endpoint controls (EDR, AppLocker, WDAC) that block unsigned Python or scripts, pinned and signed artifacts.
- Rollout and operations: deployment through the company's own tools (GPO, Intune, Ansible, MDM) instead of a double-click, secrets from a vault, fleet inventory and health at scale, tenant separation, compliance evidence (SOC 2 style).
Related: the double-click setup tool entry, the command-per-operating-system entry, and the worker-choice route-cost entry.

## Purpose: fewer AI tokens by offloading work (discussion; not a claim yet)
Question from the user: can a worker or fleet reduce AI token use by taking work away from the model? Honest position (2026-11-21): offloading a SLOW command does not by itself save tokens (waiting costs time, not tokens); tokens are saved only where the work changes what enters the model's context or how many turns it takes. Real levers, each measurable: (1) a compact result instead of raw output (a `run-tests` class that returns pass/fail and only the failing names, versus a transcript of thousands of lines), (2) one job replacing several tool calls and retries (build, run, parse in one class), (3) results kept in the results repository and reusable (the answer to "did this commit pass" asked again costs a lookup, not a run and a transcript), (4) an AI sub-task run on a worker with its own context that returns only a patch or a summary (the parent context does not grow), which shifts spend to another account rather than removing it, (5) no polling loops (`--wait` blocks instead of the agent asking repeatedly). To make it a selling point it has to be MEASURED, not asserted: record per job the raw output size, the size actually returned, the number of calls replaced, and an estimated token figure (bytes / 4 as a rough measure, labelled as an estimate), show the total in `ct-run jobs` or a new summary command, and run a small benchmark (the same task with and without offloading, counting real tokens from the model's own usage report). Related: the `offload log/fit/profile` commands rank commands by duration; add a column for output size.

## Direct compress: the full memory fix, client and worker (explained to the user 2026-11-25; follows 4c)
After 4c (streamed compression) a 1.1 GB set still costs about 1x its size on the client and about 2x on the worker. Two separate later tasks, independent of each other:
- **Client, contents out of memory.** `collect_dir`, `totals`, the summary card and `plan_batches` keep paths and sizes, not contents; each file is read from disk twice (scan, then compress). Client peak falls from about 1x to tens of MB at any set size. Costs: double disk read; a file that changes between scan and send needs a rule (re-check size and mtime). Touches files the orchestrator slices edit: start after theme/orchestrator settles. No wire change.
- **Worker, one file at a time.** Unpack now decompresses to the full bytes and `json.loads` makes a second copy (about 2x peak on small spare machines; safe because the cap counts memory, but it refuses sets a file-by-file unpack could take). Fix: tar inside zlib, a new codec name, so a wire-format change with the same compatibility rules as the first one (`compress` capability in registry.json; client refuses or falls back for a worker without it; every worker updated again). Choose which first by which side runs out of memory in practice.
