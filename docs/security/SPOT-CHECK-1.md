# Security spot-check 1 (2026-11-22)

A read-only review of what changed most recently, taken together: the Direct transport and the decision to drop profile-run approval on it, files attached to a job (names, symlinks, secrets, ignore rules), the vendored templates, the Windows worker, and how changes reach `main`. Two findings were reproduced with a script; the rest are from reading the code. **CVSS 4.0 vectors are my estimates**: confirm each in the calculator (https://www.first.org/cvss/calculator/4.0) before treating a rating as fixed. CVSS ranks a finding; it does not score the app.

## What held up

- The mailbox account is `restrict,command="..."`: no shell, no forwarding, no tty; the forced command only allows git on the two repositories (`mailshell.decide`).
- The approval key and the mailbox key are different keys. A registry change needs the approval key's signature (`update.py`, `approvals.check_registry`), so a stolen mailbox key cannot add a class.
- A job file is validated on the worker (class in the installed registry, typed parameters, age limit, names), and the refusal catalog now makes each of those rules visible and reviewable.
- Approvals are pinned to the exact job file by its digest; a job that changed after you looked is not approved.
- Output is scanned before it is published; the approval and mailbox key folders are mode 0700.

## Not examined (next spot-check)

The jail itself (bubblewrap options, namespaces), the update and install path (tags can move; how `ct-update` verifies what it installs), the Windows PowerShell scripts beyond their argument checks, the output scanner's bypasses, how `gh` tokens are handled, and denial of service by many small jobs. The AI layer has no code yet: an agent that can submit jobs is the largest open design question (a human is no longer the gate).

## Order I would fix them

F2 and F1 first (both are in one function, small, and F2 is a code-execution path), then F8 (a test), F3 (before any Windows class takes files), F4 and F5 as part of the Direct work, F6 with the pre-job summary, F7 as a decision about process.

## Status

- F1 (links) and F2 (git run in an untrusted repository): fixed in `ct.client.submit` (`safe_git`, links never followed), each with a test that failed before the fix.
- F8 (vendored templates not scanned): fixed. Every file is pinned by hash in `src/ct/client/ignore_templates/SHA256SUMS` (written by `scripts/refresh-gitignore`); `tests/test_ignore_templates.py` fails on any edit, addition or removal, and `submit.templates_problems()` makes a folder fall back to the interim rule if the templates are not exactly what was vendored.
- F7: decided: security-sensitive paths are merged by hand (`MERGE-POLICY.md`).
- F6: fixed in `pre-job-summary` (secret-looking text is held on the GitHub transport, warned on Direct; a pre-job summary card names the count, size and destination).
- F5: fixed in two parts. Part 1 (`direct-compress`): a Direct set over 1 GB is sent compressed, and the worker unpacks it only under a cap (a quarter of free disk, half of free memory, at most 10 times its job-file ceiling) after a free-disk check; the unpacking stops at the cap whatever size the job claims (`jobs.unpack_files`, tests in `tests/test_direct_compress.py`). Release compatibility: a worker advertises `compress` in registry.json from the release that added it; a client never sends compressed to a worker that does not, and the refusal names `--no-compress`. Part 2 (`fix/direct-intake-limit`): the first part left the push itself open, because the worker's job ceiling was checked only after the job file was in the queue repository, so a client holding the mailbox key could put any amount on the disk (reproduced: a 300 MB push accepted by an unconfigured bare repository). `ct-mail-shell` now holds a push to the worker's own numbers BEFORE git writes it (`ct.intake`, shared with the worker): none while free disk is below the reserve (10% of the volume, at least 2 GB; refusal `job.push.disk_nearly_full`), and git stops reading a pack over the job ceiling plus 16 MB (`receive.maxInputSize`; refusal `job.push.too_big`, nothing stays on the disk). Repeated small pushes add up only to the reserve, then are refused. Tests: `tests/test_intake.py` (the real-git test fails on the old shell). Limits that remain: on a Windows worker the owner's `hardware.max_job_mb` is applied by the worker only (the launcher does not pass it), and the disk the mailbox sits on is the one measured. The worker-side file cache of the delta-sync work (`[cache] max_mb`) is on `theme/offload-value`, not in main: it needs the same accounting when that theme lands.
- F3 (Windows file names): fixed. `jobs.file_name_problem` refuses `:`, `< > " | ? *`, a trailing dot or space and device names (CON, PRN, AUX, NUL, COM1-9, LPT1-9, with or without an extension) in any path component on a Windows worker (`8eb2d08`); the worker re-runs the same check where it writes and keeps the inside-the-folder check; the client applies it before sending when the worker's published platform is Windows (`submit.worker_is_windows`, for collected files and `--file`). `tests/test_file_name_guard.py` fails if a loop writing job files skips the check.
- F4: fixed in four slices. Slice 1 (`direct-profile-approval`): a profile run starts unapproved only where a jail isolates, never on Windows. Slice 2 (`direct-key-rotation`): `ct-setup rotate-key`. Slice 3 (`feat/direct-job-record`): the worker records every job the mailbox key sent (`ct-worker received`, `ct-admin received`, `tests/test_received_jobs.py`). One key per worker holds by construction (each worker has its own `client_home`). The Direct default stays `none` now that all of these exist; the key is still passphrase-free by design, so a copied key still queues jobs inside the jail until it is rotated, and the record is how it is noticed.
