# Windows worker loop (slice 4d of WINDOWS-SPECIAL-USE.md)

**Goal.** `python -m armada.cli run` works on Windows: it starts under the `armworker` account from the Scheduled Task, reads its configuration, keeps its state, receives a job over the Direct transport, runs it with the job runner and writes the result, so a person's computer can send a job to a Windows worker and get its result back.
This is too big for one branch; it is three small ones, each with its own done-when.

## 4d-1 Configuration and start-up (this branch)
**Done when.** (a) A worker configuration with Windows folders (`C:/ProgramData/armada/...`, forward slashes) loads and gives the right folder for every item, with system folders refused: unit tests that run anywhere. (b) On the real Windows 11 VM, `python -m armada.cli help`, `status` and one `fetch` pass start as `armworker` from the release folder with that configuration and fail only for what is not there yet (no queue), with the real error text kept; the list of what else breaks on Windows is written here. (c) The Linux suite is unchanged.
**Not in scope.** Receiving a job, running one, writing the configuration file from the installer, the privileged helper (Linux only), file locks, the state publishing details.
Decisions: Windows folders are written with forward slashes and a drive letter (`C:/ProgramData/armada/state`): Python and git on Windows accept them, and no backslash can reach a shell. The run folder and the helper socket path live under the state folder (there is no `/run`).

## 4d-1 result (run on the real Windows 11 VM, as the administrator account)
- `armada.cli help` and `armada.cli status` work: memory, disk and the state read from the configuration (heat is "unreadable": no sensor, as on a VM). The worker's Windows unit tests (21) pass there.
- Found by running it, and fixed: the context built `LinuxSensors` directly (now `runner.default_sensors()`); the file lock was unwritten (now `msvcrt.locking`, tested across two processes); `git` was not on the worker's PATH (the start task now puts `tools\git\cmd` first on the worker's own PATH, never on the system PATH).
- Next failure, by design (what is not there yet): `fetch` / `run` stop with a raw `FileNotFoundError` for `config\registry.yaml`, which the installer slice will write. A raw traceback is not an acceptable end-user message: the installer slice must make the worker say plainly that it is not set up and what to run (both operating systems share the path).
- Not run: as `armworker` through the start task (needs the registry and queue first), a reboot.

## 4d-2 The Direct transport to a Windows worker (scope)
**Goal.** Your computer pushes jobs to, and reads results from, a Windows worker over SSH exactly as it does for a Linux one: as a restricted mailbox account whose key can run only git on the worker's two bare repositories (`queue.git`, `results.git`), through the same mail shell.
**Done when.** On the real Windows 11 VM: the mailbox account, its folders and ACLs, the two bare repositories, the shell launcher and the client's public key are set up by one idempotent step (`winmailbox.ensure`); from the Mac, with only the mailbox key, `git push` to the queue works, `git ls-remote` on the results works, a push to the results and any other command are refused with the shell's own message; a second `ensure` changes nothing; and the account is not an administrator and cannot read the worker's state or config.
**Not in scope.** Writing the registry or the worker's configuration (installer slice), running the worker loop against the queue (4d-3), GitHub transport, the setup tool's check-in.
Facts that shape it (to be confirmed by probes on the VM before they are relied on):
- The client's push runs `git-receive-pack '<path>'` over SSH; the forced command (`restrict,command="..."` in the account's authorized keys) must be a launcher file that puts the tools' git on PATH and starts `python -m armada.mailshell`. The mail shell must treat `/C:/ProgramData/...` and `C:/ProgramData/...` as the same path, case-insensitively.
- The URL for a Windows path needs a leading slash: `ssh://user@host/C:/ProgramData/armada/state-mail/queue.git`.
- Git on Windows refuses repositories owned by another account ("dubious ownership"): the launcher trusts exactly the one repository, for that one command, as the Linux shell does.
- Where the account's key file lives on Windows OpenSSH (a profile that does not exist before the first login, or a Match block in sshd_config) is decided by a probe.

## 4d-2 result (run on the real Windows 11 VM, from the Mac)
`winmailbox.ensure` set up the mail account (`armada-mail`, a standard user with no interactive or remote-desktop logon), the two bare repositories under `state-mail`, the launcher and the key file, and a marked `Match User` block in sshd_config (checked with `sshd -t`, backed up, restarted); a second run changed nothing. With only the mailbox key, from the Mac: `git ls-remote` on the results works, `git push` of a job to the queue works and reads back, a push to the results is refused, any other command is refused, and another repository path is refused, all with the mail shell's own message. As the worker account (a one-time task): it reads and clones the queue, writes the results, and its push to the queue is rejected. `winmailbox.remove` undoes the account, the sshd_config block and the git trust and keeps the mailbox contents.
Probe finding (decided the sshd_config route): a Windows account that has never logged in has no profile, and a key file placed in `C:\Users\<name>\.ssh` was not used; `Match User` with an `AuthorizedKeysFile` under ProgramData worked.
Not run: the worker loop reading a job from the queue (4d-3), the client side `arm-setup` writing the key (installer slice), a reboot, Windows 10. The sshd_config edit changes the computer's SSH server settings for one account; it is marked, reversible and the only change to that file.

## 4d-3 split: the worker's files, then the first job
**4d-3a (this branch) goal.** The worker's own files exist on the Windows computer: `config\armada.toml` and `config\registry.yaml` (one portable Windows test class), the state folders, and the worker's two clones of the mailbox repositories (`state\queue`, `state\results`), with git told to trust exactly those clones. **Done when,** on the real VM: `winfiles.ensure` writes them idempotently (a second run changes nothing), and `python -m armada.cli fetch` and `step` start with that configuration, as the administrator first and then as `armworker` through the real start task (read from `state\worker.log`), failing only for what the next slice adds, with the real error text.
**Not in scope.** A job running (4d-3b), approvals and signatures (the test class is `tier: auto`), choosing the registry from the queue repository's packs, the installer's questions, the privileged helper.
Decision: the clones are made as the administrator and git is told (in the tools git's own system configuration) that they are meant, instead of switching to the worker account to clone: switching needs a password reset that would break the Scheduled Task's stored logon.

## 4d-3a result (run on the real Windows 11 VM)
`winfiles.ensure` wrote `config\armada.toml`, `config\registry.yaml` (the new `windows-core` pack: `win-status`, `win-echo`, both `tier: auto`, `network: true`), the worker's own state folders and its two clones of the mailbox repositories, with the tools git told to trust exactly those clones; a second run changed nothing. `fetch` and `step` run clean on an empty queue. Started through the real Scheduled Task as `armworker`, the loop (`armada.cli run`) stayed running (process owner read back from the system as the worker account, task state Running), with nothing new in `worker.log` and the lock and sync files in its state folder touched while it ran.
Found by running it, and fixed: the worker needs PyYAML (the tools installer now installs it by hash, `--require-hashes --only-binary --no-deps`, only when `import yaml` fails; repeat unchanged); `git clone` of an empty repository writes a warning that PowerShell 5.1 turned into a failure; and the release fetch REPLACED the `release` folder, which threw away the worker account's access written by the layout step (the loop then could not even import `armada`): the fetch now copies the verified release INTO the existing folder with `robocopy /MIR /COPY:D`, so files take the folder's access; checked across three fetches of different commits.
Not run: a job going through (4d-3b), a reboot, Windows 10. Note: the `cmd_run` loop does not write `pass-status.json` (only the timer-style `fetch`/`step` commands do), so "the loop ran" is shown by the lock and sync files, not that file.

## 4d-3b result: the first job, end to end (run on the real Windows 11 VM, from the Mac)
`scripts/win-job-check USER@HOST` sets up what it needs (all idempotent), then does what `arm-run` does with the client's own code: pushes a `win-echo` job to the Windows worker's mailbox over SSH, lets the worker (running as `armworker` through the Scheduled Task) fetch and run it, and reads the result back. Result: status `ok`, exit code 0, output `"hello from the Mac 193248"`, with the run's measurements, about 25 seconds after the push (the loop polls every 20 s). The task, its processes and the job all ran as the worker account.
Two Windows-only problems found by running it, fixed, each with a test:
- The worker decides whether a job is still alive by reading the process's command line (`/proc` on Linux), which is empty on Windows, so every job was declared dead the instant it started ("job process ended without a result"). `plat.process_cmdline` now reads it with `NtQueryInformationProcess` (class 60).
- The worker refused every job ("this machine cannot isolate jobs (bubblewrap is not installed)"). Windows has no jail to build: it now uses a `WindowsJobObject` jail that says plainly it is a Job Object per job and no file or network isolation (Special Use by design; the registry already refuses classes that need no network there).
Notes: `cmd /c echo` prints its argument with the quotes the job runner puts around a text containing spaces (the class's regex already keeps shell characters out); the result's first publication says `running`, so a reader waits for a final status.
Not covered: approvals and signatures (the class is `tier: auto`), `arm-run` itself (this used its library, not the command), a reboot, more than one job at a time.

## 4e Installer wiring (run on the real Windows 11 VM, from the Mac)
`arm-setup add-worker <windows address>` now does the whole job for a Windows computer, through the same registration as any worker (`install_worker`): it says what it will and will not touch and asks; writes this computer's own configuration for the worker (`<name>.toml`, with its client folder, kept as it is when it is already there); makes the mailbox key here (only the key type and the key go to the Windows computer, never a comment); runs the tools, accounts and folders, release, mailbox, worker files and start-task steps over SSH (`src/armada/setup/winsetup.py`, each step idempotent, each failure stopping with the real error text and "run the same command again"); clones the two mailbox repositories here; and proves the loop with a first job (`win-status`) sent the way `arm-run` sends one. Run for real against the VM with an isolated client configuration: every step reported, first job `ok`, the worker registered; then the real `arm-run classes` listed the Windows classes and `arm-run submit win-echo -p text=... --wait` returned `ok` with the text, in 11 seconds (6 s noticing, 1 s running, 4 s coming back).
Needs a Windows release tag that holds this code: `release-win-0.1.0` predates the Windows worker, so a normal install has nothing to fetch until a new tag (for example `release-win-0.2.0`) is cut after this merges. Until then `ARM_WINDOWS_RELEASE_COMMIT=<commit>` installs a given commit (testing only).
Found by the unit tests: the mailbox key's comment held spaces, which the mailbox step's one-line key check rightly refuses; only the type and key are sent now.
Not covered: removing a Windows worker (`arm-setup uninstall` knows only Linux workers), a reboot, `arm-admin` commands on a Windows worker beyond `workers` and `status` (apply refuses it by design), approvals and signatures on Windows, the double-click setup tool.
